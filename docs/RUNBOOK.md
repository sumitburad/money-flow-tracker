# Global Money-Flow Monitor — Operator Runbook

Plain-language steps for the owner are in `START_HERE.md` at the repository root. Links and steps for every free provider and key are in `docs/CONNECT_DATA_PROVIDERS.md`. This page is the technical companion.

## Normal operation
- `Daily money-flow refresh` (`.github/workflows/daily.yml`) runs from schedules at 02:07 and 13:37 UTC (07:37 and 19:07 IST), every day. Backup schedules at 04:37 and 16:07 UTC (10:07 and 21:37 IST) run only if `docs/status.json` does not already show a complete snapshot for that morning or evening session (`scripts/should_run.py`). A skipped backup still costs about one billed minute.
- **Run workflow** (workflow_dispatch) starts a run by hand. A manual run always runs. A push or merge to `main` does not start a run.
- Steps: gate, collect (up to 3 whole attempts, 60 s and 120 s apart), validate the feed, top up history (`--mode update`, may fail without failing the run), sync the dashboard files, commit and push (up to 4 attempts), write a plain-language run summary, upload artifacts on failure.
- GitHub's scheduling is best-effort. Use the feed's **actual collection time** (`generated_at_utc`, and `collected_at_utc` per item), never the scheduled time, for freshness. The dashboard banner is green to 20 hours, amber to 48 hours, red beyond that.
- PRs run `Global monitor checks` (`.github/workflows/tests.yml`).
- `Load official history` (`.github/workflows/history.yml`) is manual only. It loads or repairs `data/history/v1/`.

## Data sources and keys
- FRED: if the Actions secret `FRED_API_KEY` is set, the FRED API is tried first, then the keyless CSV, then the DBnomics mirror. The key is redacted from any error text and scrubbed from every JSON file written. It must never be committed, printed or placed in `status.json`.
- Groq and OpenRouter (optional secrets `GROQ_API_KEY` and `OPENROUTER_API_KEY`): Groq is tried first when its key exists, then OpenRouter. Groq sign-up did not work for the owner (22 November 2026), so only `OPENROUTER_API_KEY` is saved and OpenRouter (`openrouter/free`) is the only AI in use. They tag official headlines (at most 3 requests of 5 headlines each, paced 8 seconds apart) and write the executive summary (1 request). Each call is retried once after a 429 answer, honouring `Retry-After` (capped at 30 s). **Empty AI answers (found in the first live run, 22 November 2026).** `openrouter/free` often picks a "thinking" model whose thinking is counted inside the same `max_tokens` limit as its visible answer. The first live run gave `AI response missing text` for the summary and refused most tagging answers, which fits a model that used its whole limit thinking (no reply was kept, so this is likely, not proven). The fix is in `backend/ai_reply.py`, shared by both AI steps: OpenRouter calls use `max_tokens` 3500 (Groq keeps 1500 for the summary and 1800 for tagging) and wait up to 75 s; an empty or cut-off reply is retried once with `reasoning: {effort: low}` added (the summary once per provider, the tagging once per run; Groq already runs at its lowest effort and is not retried); a model's thinking text is never used as an answer. A refresh makes about 4 requests and at most 10. The status file now says why an AI answer was refused: `executive_summary.reasons` and `ai_classification.failure_reasons` give the status code and what it means, the provider's own words, the model that really answered and how often it happened; `models_seen` lists the models that answered and `empty_reply_retries` counts the second tries. Keys are always redacted from these texts. Groq's free plan allowed 30 requests a minute, 1,000 a day, 8,000 tokens a minute and 200,000 tokens a day (checked 22 November 2026). **OpenRouter's free limits** (checked 22 November 2026 on OpenRouter's pricing and free-models pages; the separate limits page could not be opened): the free models (names ending in `:free`, which `openrouter/free` picks from) are capped at 20 requests a minute and 50 a day, rising to 1,000 a day once about $10 of credit has been bought (the per-minute cap stays 20). OpenRouter's guides say failed attempts still count against the day's total. About 4 requests on 2 to 4 runs a day is 8 to 16 requests (at most 40 if every request needs its one retry), which fits inside 50; each manual **Run workflow** adds about 4. A 429 caused by the daily cap does not clear by waiting, so the one retry is wasted there and the rule-written summary is the fallback. Default model names are set in code (`backend/news_classifier.py`, `backend/exec_summary.py`) and listed in `config/models.yaml`; for OpenRouter's default `openrouter/free` the models actually asked are chosen at run time (next paragraph). If a provider retires a model, the AI step falls back to rule-written text and says so; update the name in code. Free models may retain prompts; the digest holds only category words, names and public business headlines.
  **Named free models (seventh pass, 22 Nov 2026).** The second live run (after PR #15, run 45014686011) showed the extra room and the `reasoning: {effort: low}` retry were not enough: the summary still got empty replies from `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free`, and tagging made 4 calls and classified 0 of 30 headlines (empty replies from `nvidia/nemotron-3.5-lightning:free`, `nvidia/nemotron-3.5-super-vl:free` and `recursive/flint-v1.0:free`). `backend/free_models.py` (settings in `config/ai_models.yaml`) therefore stops using the random router when it can. Once per run (`POOL`, shared by both AI steps) it reads `GET https://openrouter.ai/api/v1/models/user` (the models this account may use; sent with the key, never logged), falls back to the public `/api/v1/models` only if the account list could not be read, follows OpenRouter's own `next` page links (own site only, at most 2 extra pages) and keeps models that are `:free` with zero prices, text in and out, no `reasoning` parameter (a model that lists one is treated as a thinker and skipped), at least `min_context_tokens` of context, an answer limit of at least `min_answer_tokens`, and a stated size of at least `min_billions` (a name with no stated size is allowed only if it matches a `prefer` word). They are ordered by the `prefer` words, then by size, and up to `max_models` (at most 3) go into the request: `model` is the first and `models` the rest, which OpenRouter uses as automatic fallbacks, in order. Only `:free` ids are ever named, because a fallback is billed at its own price. Each retry starts one model further on. A model named in `OPENROUTER_SUMMARY_MODEL` or `OPENROUTER_CLASSIFIER_MODEL`, and Groq, are never changed, and only a request to the real `openrouter.ai` host is rewritten. Any problem (list unreadable, nothing suitable, feature switched off with `enabled: false`) means no choice: the request goes to `openrouter/free` as before. The status file records `free_pool` (the ids), `pool_counts` (how many were seen and why others were skipped) and, when nothing could be chosen, `pool_note` in plain words; the summary's `model` is now the model that really answered (the response's own `model` field), so a fallback is visible. The dashboard's Data quality box shows an "AI models:" line, or the `pool_note` as a warning. Not proven live: that the account list matches the documented shape, that the chosen models accept the request and pass the answer checks, and whether OpenRouter counts a fallback attempt against the 50 a day. OpenRouter lists only models the account's privacy settings allow (free models may retain prompts), so an account that has switched that off may get an empty list; the note then says so.
- Every outbound request uses the shared client in `backend/net.py`: 3 attempts with growing waits, `Retry-After` honoured, and a per-host breaker that stops retrying a host after two fully failed calls in the same run.
- `docs/status.json` carries `run_slot` (morning/evening/backup/manual), `completed_at_utc`, `needs_retry` and `official_source_problems`. If an official source keeps failing, `needs_retry` stays true and the backup slots will keep running, which adds billed minutes (my estimate: roughly 12 a day) until the source recovers.

## Actions minutes (cost)
GitHub Free personal accounts include 2,000 Actions minutes a month for private repositories, and every job is rounded up to a whole minute (GitHub Docs, checked 22 November 2026). My estimate is about 10 to 15 minutes a day for two main runs plus two mostly skipped backups, so roughly 300 to 450 minutes a month. It is an estimate, because the workflow has not yet run on GitHub. Check the real figure on GitHub's billing page after the first week. Each job also has a hard time limit (25 minutes for the daily refresh, 20 for history), which caps the cost of a stuck run. The pacing adds time to each run: 8 seconds between AI tagging requests (at most 16 seconds) and 5.5 seconds between the ten market-news questions (about 50 seconds). Expect a run to be 1 to 2 minutes longer than before the news feature.

**Decision, 22 November 2026:** the free private-repository minutes for the month were used up, so the owner makes the repository public. Standard GitHub-hosted runners are free for public repositories, so the cost becomes zero. If the repository is kept private instead, minutes beyond the free allowance cost $0.006 a minute on the standard Linux runner, about $1.80 to $2.70 a month at the estimate above (GitHub Docs, checked 22 November 2026).

## Flow windows, rotation and executive summary (added 2026-11-22)
- `config/flow_windows.yaml` holds the windows, the flat bands, the session-close times, the maximum data age and the bucket list. `backend/flow_windows.py` computes a day, week and month signal per item from the daily bars already read in memory, and a rotation block per bucket. Only categories reach the feed (`flow_windows` per item and a top-level `rotation`). No price, volume or percentage is written anywhere. The rules are in `config/label_rules.md`.
- The newest bar is used only once its market session is over (`session_complete_after_utc`; 24-hour markets use the last full day). A morning run can therefore show Asian markets for the day just closed and the US market for the previous US day. That is expected.
- `backend/exec_summary.py` builds the dashboard's executive summary. The model sees a digest of categories and names only. Its answer is validated (fields, length, no digits, no advice words, no links, only known names); otherwise a rule-written summary is used. The feed's `executive_summary.method` is `ai_validated` or `rules_only`, and `human_review_required` is always true.
- Health: the run's health block carries `flow_windows` (how many items have a signal and how many lack volume) and `executive_summary` (providers tried, answers rejected, reasons). The run summary box shows both in plain words.
- If a ticker returns nothing, the item shows as unavailable in the dashboard's Data quality box. The 23 tickers added on 2026-11-22 have not been tested live; read that box after the first run and fix or remove any that fail in `config/universe.yaml`. Every investable item must sit in exactly one bucket of `config/flow_windows.yaml`; a test fails otherwise, so change both files together.
- `config/universe.yaml` may set `session_market` on an item to choose which market's close decides whether its newest bar is complete (China is set to the US session, spot currencies and the dollar index to 24H).

## Risk banner, events calendar and market news (added 2026-11-22, second pass)
All three are additive feed blocks (`regime`, `calendar`, `market_news`); the schema stays `1.0`, and each is optional for readers. None of them can fail a run, and none sets `needs_retry`: their error sources (`calendar_fred`, `calendar`, `market_news`, `regime`) deliberately do not match the official-source pattern in `backend/run_daily.py`, so a news outage never starts the backup slots. They only turn `status` to `degraded` and appear in the dashboard's Data quality box, in `docs/status.json` (`regime`, `calendar`, `market_news`) and in the run summary box (lines **Risk tone**, **Coming events**, **Market news**).

- **Risk banner** (`config/regime.yaml`, `backend/regime.py`, contract `validate_regime`). Eight checks over the same completed daily closes the flow windows use (never fetched twice): four trend checks (stock markets, fear gauges, dollar, crypto) and four relative checks (junk versus government bonds, growth versus defensive sectors, small versus large companies, copper versus gold), voted for the week (5 sessions) and the month (20). A trend check needs a strict majority of members with data; a relative check needs the basket mean returns to differ by at least `min_gap_pct` (0.75 week, 1.5 month). Label rule: at least 5 checks with data, at least 60% leaning one way and at most 1 the other gives `risk_on` or `risk_off`; otherwise `mixed`; fewer than 5 gives `not_enough_data`. The headline label is the month's, with the week's as `short_term_label` and a `shift`. Only words and counts are published (no price, no return, no score). The contract validator recomputes the tally and the label from the published rule, so a feed whose label disagrees with its own votes is rejected. A model never sets this label (`config/label_rules.md`). To change a member list or threshold, edit the yaml; tests in `tests/test_regime.py` pin the rule.
- **Coming events** (`config/events.yaml`, `backend/events_calendar.py`). FRED `releases/dates` (needs `FRED_API_KEY`) is matched by release name, so each `fred_release` must equal FRED's own name. A name that finds no upcoming date is listed in `status.calendar.fred.unmatched_releases` and in the Data quality box; correct the name in the yaml. The Fed meeting dates are a built-in list compared with the Fed's own pages on 2026-11-22 (`checked_against_official_site: true`, `checked_on: "2026-11-22"`): the eight 2026 decision days and the seven 2027 ones the Fed has published. The Fed calls its 2027 schedule tentative and revised it on 2026-11-12, so re-check https://www.federalreserve.gov/monetarypolicy/fomccalendars.htm whenever it announces a change, and move `checked_on` (or set the flag to false if you cannot check). The 26-27 October 2027 meeting is a policy-strategy meeting with no rate decision, so it is left out. The list ends on 2027-11-30 (`covers_through`); once the horizon passes that date the health block carries an advisory, and the next calendar must be added. Only dates are shown, never a forecast. The FRED request settings (`realtime_start`, `realtime_end`, `include_release_dates_with_no_data`, `order_by`, `sort_order`, `limit`, `offset`) and the answer shape (`release_dates` with `release_id`, `release_name` and `date`) match FRED's documentation page for `fred/releases/dates`, and the six release names match FRED's own release-calendar pages (both seen 2026-11-22). Not yet proven: a live call with the real key from GitHub's runners.
- **Market and company news** (`config/market_news.yaml`, `backend/market_news.py`, contract `validate_market_news`). GDELT DOC 2.0 `artlist` JSON, keyless, at most 10 questions (6 themes and 4 company groups) paced 5.5 seconds apart; the HTTP client's per-host breaker (its own instance, three tries per question) stops after two fully failed calls. Each question is tried up to 3 times (`default_http()`: waits of 10 s and then 20 s between tries, or the index's own `Retry-After` if longer, at most 30 s), and each try waits up to 45 s for an answer (10 s to connect, `timeout_seconds` in the settings file). The whole step stops asking after 330 s (`source.total_seconds`); a dead index costs about that much at most before the breaker trips (after two questions that failed all three tries), and a slow one can never hold the refresh up (the job's own limit is 25 minutes). The status file records `seconds`, `slowest_answer_seconds` and `queries_skipped`, and failures are plain sentences such as "no answer from the news index within 45 seconds (3 tries)"; a refusal carries the server's own words and any `Retry-After`, for example "news index answered HTTP 429 (it said: Please limit requests to one every 5 seconds; it asked for a wait of 5 seconds)" (`_said()`: at most 90 characters, markup and web addresses removed, secrets redacted), which tells a throttle from a block. First live run (22 November 2026): the index was reachable but two questions timed out at the old 25 s limit, so no news was shown; why it was slow is not proven, so the next live run's `slowest_answer_seconds` is the number to read before changing anything else. Second live run (22 November 2026, after the 60 s fix): the first two questions each got HTTP 429 twice (6 to 12 s waits), the breaker opened after two questions and the step ended after 59 s with no headlines. GDELT's DOC API answers 429 with a request to limit calls to one every 5 seconds, and its limits are reported to vary by address, so shared GitHub runner addresses may be throttled before our first question; whether more patience cures it is not proven (the next live run's note shows what the index says). If GDELT still fails, the options are the publishers' own RSS feeds (each needs its licence read first) or a news service with a free key such as Finnhub; both need Sumit's decision and neither is built. Only headlines from the 14 listed publishers are kept (the host must equal or be a subdomain of a listed domain; https and port 443 only; no credentials in the link), English only, at most 72 hours old, deduplicated by normalised title, capped at 36 stories (14 about companies, 6 per publisher). A company counts only when its name appears in the headline itself. Only the headline, publisher, link and time are stored; there is no article text. The dashboard builds the page with `textContent`, so hostile headline text cannot inject markup. The executive-summary prompt marks headlines as untrusted and the validator still rejects digits, links and advice words. Switch the feature off with `enabled: false` in `config/market_news.yaml`. Checked against GDELT's own pages on 2026-11-22 (read through search results, because the pages could not be opened directly): the DOC 2.0 API searches a rolling window of about the last three months, `sort=hybridrel` appears in GDELT's own example links, and GDELT says its APIs are rate limited (the pages gave no number, so the 5.5-second spacing stays as a cautious assumption). Its About page says its datasets may be used without limit, commercially too; the rest of that paragraph, which may ask for a credit, was cut off, and the dashboard already names GDELT with a link under the news. GDELT answered a badly written question with a short plain-words message (seen once, in an HTML answer); `ask()` already treats any answer that is not JSON as a failed question. Still unverified: GDELT's exact JSON answer shape for `format=json` (no answer has been seen yet) and whether 60 s per question is enough.
- **Shared-host note.** The daily FRED series and the release calendar both go to `api.stlouisfed.org` through the same client, and its breaker is per host. If two FRED series calls fail completely in one run, the calendar call is skipped in that run (`calendar_fred` error, Fed meetings still shown). That is deliberate: FRED is already failing, and a retry would only add load. A successful FRED call resets the count.
- **Inflation charts.** `config/history.yaml` (`fred_yoy`) lists CPIAUCNS, CPILFENS, PCEPI and PCEPILFE. `scripts/backfill_official.py` computes the change from a year earlier (`method: year_on_year_percent`) and keeps no index values. The base index is fetched one year before the start date so the first row can be calculated. The dashboard draws one two-line chart for CPI and one for PCE (all items and core). They appear only after **Load official history** has been run.

## On failures
1. Open the repo Actions page and the failed run. The run summary box lists, in plain words, status, collection time, current items, macro series and problems. Do not infer completion from a scheduled trigger.
2. Check `docs/status.json` and `data/health/YYYY-MM-DD.json`. The latter contains missing universe IDs and categorical provider errors.
3. If all inputs failed, no new feed or label is produced. The previous `latest.json` remains, clearly dated, and the dashboard banner turns amber, then red.
4. A price-only failure should not be covered by a macro figure. Missing direct fund flow always caps the related asset at Neutral/Mixed.
5. On unofficial price-provider blocks, **do not** bypass captchas, authentication or terms. Use authorized alternate histories for private research; do not copy them into the repo.
6. Review daily `data/feed/v1/latest.json`, and compare stale dates with official market calendars. Saturday morning may contain Friday's U.S. close; Indian exchanges can be shut. Note that `data/feed/v1/daily/YYYY-MM-DD.json` is overwritten by a later run on the same IST date.
7. Use a reviewed PR and green tests to change rules. Never change past archived labels in order to improve historical results.

## Official history (`data/history/v1/`)
- Start date 2021-11-22, set in `config/history.yaml`. Official-source data only; no price data. Plain CSV per series plus `manifest.json`.
- FRED series DFF (policy rate), T10Y2Y (yield-curve slope), T10YIE (10-year breakeven inflation) and UNRATE (unemployment, monthly, 35-day availability lag) were added on 2026-11-22. Run **Load official history** once to load them.
- `available_from_estimate` is a conservative publication-lag estimate, not a vintage date. Values are the current vintage; later revisions are not tracked. Backtests must filter on this column.
- Manifest statuses: `ok`; `kept_previous` (today's download failed, the earlier good file is still there); `missing` (never loaded); `no_matching_contract` (CFTC data was fetched but no contract matched the name pattern).
- If a CFTC market shows `no_matching_contract` (history) or the status file lists `cftc_market:<id>` (daily), open `data/history/v1/cftc/contracts_seen.json`, find the real contract name, and correct `CFTC_MARKETS` in `backend/advanced_sources.py`.
- **Found in the first live run (22 November 2026):** only the dollar index matched. The exchanges renamed the contracts in February 2022, so `contracts_seen.json` holds both names for each market, for example `E-MINI S&P 500 STOCK INDEX` until 2022-02-01 and `E-MINI S&P 500` after it, `NASDAQ-100 STOCK INDEX (MINI)` then `NASDAQ MINI`, `10-YEAR U.S. TREASURY NOTES` then `UST 10Y NOTE`, `U.S. DOLLAR INDEX` then `USD INDEX`. The old patterns were not anchored, so they also matched look-alikes (Micro E-mini, Ultra 10-year, "Consolidated") and a day with two matches is dropped as ambiguous. Each market now lists its old and new name, anchored to the start of the name and followed by ` - ` or the end (`backend/advanced_sources.py`); `tests/test_advanced_sources.py` holds the real names and the look-alikes. `update` and `backfill` do the same work, so the next daily refresh rebuilds the CFTC history by itself. Confirmed only after the next live run.
- Four year-on-year inflation series (`CPI_YOY`, `CPI_CORE_YOY`, `PCE_YOY`, `PCE_CORE_YOY`) are calculated from FRED price indexes and added to the manifest with `method: year_on_year_percent` and a `group` and `line_name` for the chart (added 2026-11-22). Run **Load official history** once to create them.
- Run **Load official history** again to repair gaps. It is safe to repeat; it rewrites only files whose content changed.

## Security and reuse
Owner decision (22 November 2026): the repository is made public so that GitHub's free minutes for public repositories apply. Treat everything committed, including older commits and run logs, as public. Never commit API keys, SSH private keys, OAuth secrets, broker tokens, account identifiers, orders, proprietary historical price tables or non-public research outputs. Broker credentials, trading-server details and any private market data stay in the private trading project and are never copied here. Never attach a self-hosted runner to this repository, and never use a machine that holds trading keys as a runner. In Settings, Actions, General, set approval for workflows from outside collaborators' fork pull requests to **Require approval for all outside collaborators**.

Actions rules set by the owner on 22 November 2026: only the owner's actions and selected others are allowed, and **Require actions to be pinned to a full-length commit SHA** is on. Therefore every `uses:` line in `.github/workflows/` carries a 40-character commit code with the version in a comment (checkout v4.4.0, setup-python v5.6.0, upload-artifact v4.6.2), and **Allow actions created by GitHub** must be ticked **and saved** or no run will start (on 22 November 2026 the first runs failed to start; after the owner updated and saved the setting, a run started and finished). To update an action, read the new tag's commit with `git ls-remote --tags https://github.com/actions/<name>`, replace the code and the version comment, and run actionlint. A tag name such as `@v4` is refused by the repository rule.

Only the research feed and history files are intended for cross-project consumption. Use `backend/feed_contract.py` for validation and retain each dated snapshot and fetch timestamp. The feed contract is additive only: `collected_at_utc`, the per-item `flow_windows` block and the top-level `rotation` and `executive_summary` blocks are optional fields and the schema stays `1.0`. A paper/live trading system needs a separate source-authority and timing approval before a signal is admitted to decision logic.
